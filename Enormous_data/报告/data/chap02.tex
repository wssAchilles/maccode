\chapter{相关技术（系统使用技术介绍）}

\section{Docker ARM64 实验环境}

Docker 用于把 Hadoop、Spark、Flask 和前端服务放入可复现的容器环境。由于本机为 ARM 架构，系统必须避免使用 \texttt{linux/amd64} 镜像和 \texttt{bde2020/hadoop-*} 这类常见 amd64 Hadoop 镜像。本项目采用自建 ARM64 Hadoop 镜像：基础层使用 Ubuntu ARM64，安装 Java、SSH、rsync、bash、procps 等必要运行依赖，再复制精简的 \texttt{/opt/hadoop} 到镜像中。这样既避免了跨架构模拟带来的性能和兼容风险，也避免了 \texttt{docker commit master} 把 HBase、Hive、日志、HDFS 数据目录和 apt 缓存一起打包成 30GB 大镜像的问题。

Docker Compose 使用 \texttt{yarn-lab} profile 组织实验集群\cite{docker_compose_overview}。服务包括 NameNode、两个 DataNode/NodeManager、SecondaryNameNode、ResourceManager、Spark submit gateway 和 Spark History Server。为了不与用户已有的 \texttt{master} 容器抢端口，HDFS UI、YARN UI 和 Spark History 分别使用 \texttt{19870}、\texttt{18088} 和 \texttt{28080}。日常前后端开发与复检以 \texttt{start-dev.sh} 为准：Flask 后端监听 \texttt{5051}，Vite 前端监听 \texttt{5173}。

\section{HDFS 与 YARN}

HDFS 负责大文件存储，核心角色包括 NameNode 和 DataNode。NameNode 保存文件系统元数据，DataNode 保存实际数据块。HDFS 的设计目标是高吞吐、大文件和故障恢复，不适合把大量小文件作为主要输入，因此本项目把 CSV 作为原始输入层，后续将清洗结果写为 Parquet 分区目录，以减少重复扫描成本\cite{hadoop_hdfs_architecture}。

YARN 是 Hadoop 3.x 中的资源管理层，主要组件包括 ResourceManager、NodeManager 和 ApplicationMaster\cite{hadoop_yarn_overview}。ResourceManager 负责全局资源调度，NodeManager 负责单节点容器管理，ApplicationMaster 负责某个应用的生命周期。Spark on YARN 会为 Spark 应用申请 ApplicationMaster 和 executor 容器\cite{spark_yarn_docs}。本项目第一阶段采用 \texttt{client} mode：driver 仍运行在 spark-client 容器内，便于 Flask/API 继续读取本地 \texttt{data/cache}；executor 由 YARN 调度到 NodeManager 上运行。该选择降低了第一阶段工程迁移风险，后续可扩展为 \texttt{cluster} mode 与 HDFS 输出。

\section{Spark SQL、RDD 与 AQE}

Spark 的 RDD 模型提供了弹性分布式数据集、lineage 容错和内存复用能力\cite{zaharia2012rdd}。在本项目中，底层执行仍由 Spark Core 负责，但业务开发主要使用 Spark SQL/DataFrame API。DataFrame 能够把列裁剪、过滤条件、join 策略和聚合计划交给 Catalyst 优化器处理，减少手写 RDD transformation 造成的不可控 shuffle。

Spark SQL 的 Adaptive Query Execution（AQE）用于在运行时根据实际统计信息调整执行计划。典型能力包括合并小 shuffle 分区、处理倾斜 join 和动态选择 join 策略\cite{spark_sql_performance}。本项目在 \texttt{configs/yarn-client.yaml} 中启用 AQE、skew join 和合理 shuffle partitions，并将 \texttt{spark.sql.maxPlanStringLength} 限制为 8192，避免 Spark History Server 因超长 plan 字符串触发 JSON 读取限制。

\section{Parquet 与数据布局}

CSV 适合作为外部原始数据格式，但不适合反复执行宽表分析。CSV 没有列式编码和谓词下推，读取时通常需要扫描大量无关列；同时 CSV 类型信息弱，清洗阶段需要额外进行 schema 推断或手动转换。Parquet 是列式存储格式，支持压缩、列裁剪和谓词下推，适合 Spark SQL 反复读取\cite{parquet_docs}。因此本项目采用“CSV 原始层 + Parquet 清洗层”的数据布局：原始 Kaggle CSV 保留在 \texttt{data/raw/kaggle/ecommerce\_behavior}，1\%/5\% 样本上传到 HDFS，清洗后写入 HDFS Parquet 目录，再进行 Parquet 输入对照实验。

\section{内存优化与数据倾斜控制}

Spark 程序常见 OOM 并不只来自 executor 内存不足，也来自 driver 端收集过多结果。本项目把优化分为两个层次。第一层是 Spark 执行层：启用 AQE、设置 executor/driver memory overhead、使用 \texttt{MEMORY\_AND\_DISK}、模块结束后显式 \texttt{unpersist()}。第二层是算法输出层：禁止把完整推荐明细、cohort 明细、forecasting 明细和 experimentation 明细全部 \texttt{collect()} 到 driver；大明细改写为 Parquet，前端只读取 preview JSON；关联分析加入 \texttt{top\_nodes} 和 \texttt{max\_pair\_products\_per\_session}，并记录 \texttt{pair\_base\_rows} 等膨胀指标。

这类优化与 Starfish、SkewTune 和 Themis 的思想一致。Starfish 强调通过 profiling 做调优，而不是凭经验猜参数\cite{herodotou2011starfish}；SkewTune 指出长尾 task 会拖垮整体作业完成时间\cite{kwon2012skewtune}；Themis 说明全内存并不总是最佳策略，合理 spill 和磁盘中间结果反而更稳定\cite{rasmussen2012themis}。本项目没有重新实现这些系统，而是用 Spark AQE、Parquet、预聚合、限流和质量报告把这些思想工程化。

\section{Flask API 与 React Ops 页面}

后端 API 使用 Flask Blueprint 提供 \texttt{/api/v1} 统一接口，响应格式为 \texttt{ApiEnvelope}，包含 \texttt{code}、\texttt{message}、\texttt{data} 和 \texttt{meta.request\_id}。Spark 运行完成后，后端读取 manifest、质量报告和 Spark History 指标，写入 SQLite 作业记录和 \texttt{data/cache} JSON 缓存。前端基于 React、Vite 和 TanStack Query 读取 API 数据，页面以业务分析模块和 Ops 运维模块组织。

本次实现新增 \texttt{/api/v1/ops/evidence} 接口，专门向前端返回精简 benchmark 证据。该接口只暴露样本、对照组、耗时、吞吐、YARN app id、质量状态、HDFS 输入路径和清理策略，不返回 Spark stderr 大文本，避免把 History Server 的超长 JSON 问题传递到浏览器。Ops 页因此可以同时展示当前运行状态、质量门禁、HDFS 输入快照、benchmark 对照表和保留的 Spark History app id。
