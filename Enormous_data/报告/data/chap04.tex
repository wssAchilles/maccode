\chapter{系统设计与实现（实现步骤截图、环境安装、代码实现）}

\section{总体架构}

系统采用“数据层、计算层、服务层、展示层”四层结构。数据层包括本地 Kaggle 原始 CSV、本地 1\%/5\% 样本、HDFS CSV 输入和 HDFS Parquet 清洗层；计算层包括 Spark SQL pipeline、AQE、推荐/关联/异常等算法模块和 Spark History event log；服务层包括 Flask API、SQLite 作业记录、run manifest 与 benchmark evidence 服务；展示层包括 React 前端业务页面、质量页和 Ops 页。

图\ref{fig:yarn-architecture}展示了 Docker YARN 实验集群拓扑。该拓扑保留了 Hadoop 课程设计所需的 NameNode、DataNode、ResourceManager、NodeManager 和 Spark History Server，同时增加 spark-client 作为提交入口。前端与后端按 \texttt{start-dev.sh} 启动：Flask 后端为 \texttt{5051}，Vite 前端为 \texttt{5173}；HDFS UI、YARN UI 和 Spark History UI 分别映射到 \texttt{19870}、\texttt{18088} 和 \texttt{28080}，避免与已有 \texttt{master} 容器冲突。

\section{环境安装与启动步骤}

\subsection{ARM64 Hadoop 镜像构建}

本项目避免使用 amd64 Hadoop 镜像，也避免把整个 \texttt{master} 容器 commit 成大镜像。最终方案是自建精简 ARM64 Hadoop 镜像，只包含运行 Hadoop 所需的 Java、Hadoop 文件、配置和启动脚本。核心思路如下：

\begin{lstlisting}[style=codexcode]
FROM ubuntu:24.04

RUN apt-get update && apt-get install -y \
    openjdk-8-jdk-headless bash ssh rsync procps curl \
    && rm -rf /var/lib/apt/lists/*

COPY hadoop /opt/hadoop

ENV HADOOP_HOME=/opt/hadoop
ENV HADOOP_CONF_DIR=/opt/hadoop/etc/hadoop
ENV PATH=/opt/hadoop/bin:/opt/hadoop/sbin:$PATH
\end{lstlisting}

与 \texttt{docker commit master} 相比，该方法不会复制 HDFS 数据目录、日志、Hive、HBase 和临时文件，因此镜像体积更可控，也符合 ARM Mac 的架构约束。

\subsection{HDFS 目录准备}

启动后需要创建实验目录，并上传样本数据。正式样本来自真实 Oct/Nov 原始 CSV 的用户级采样，不再使用 87.4KB smoke 文件作为论文结论依据。

\begin{lstlisting}[style=codexcode]
docker compose --profile yarn-lab exec spark-client \
  /app/scripts/init_yarn_lab.sh
PERCENTS="1 5" ./scripts/prepare_yarn_samples.sh
\end{lstlisting}

\texttt{init\_yarn\_lab.sh} 的作用是等待 HDFS 可用、创建 \texttt{/user/course} 与 \texttt{/spark-history}，并按参数上传样本文件。正式实验中，\texttt{prepare\_yarn\_samples.sh} 会从本地用户级样本准备 1\% 和 5\% 输入，再上传到 HDFS 对应目录。这样 HDFS 中的数据来源可以追溯到本地样本文件和原始 Kaggle CSV，而不是手工复制的不明来源文件。

清理后的 HDFS 关键路径包括 1\%/5\% CSV 输入、YARN-only/AQE/algorithm/Parquet 的处理输出，以及 6 个最终 Spark History event log。旧的 \texttt{application\_178098*} 和 \texttt{application\_1780991452919\_0001} 到 \texttt{0005} 大日志已经清理，避免继续触发 Spark 3.5.5 History Server 的 JSON 长字符串限制。

\section{Spark 提交链路实现}

\subsection{YARN client 配置}

第一阶段采用 YARN client mode。这样 driver 运行在 spark-client 容器，Flask 仍可读取本地 \texttt{data/cache}，前端也能继续使用原有缓存文件。核心配置包括：

\begin{lstlisting}[style=codexcode]
spark:
  master: yarn
  deployMode: client
  appName: ecommerce-yarn-lab
  config:
    spark.sql.adaptive.enabled: true
    spark.sql.adaptive.skewJoin.enabled: true
    spark.sql.shuffle.partitions: 64
    spark.sql.maxPlanStringLength: 8192
    spark.eventLog.enabled: true
    spark.eventLog.dir: hdfs:///spark-history
\end{lstlisting}

\texttt{spark.sql.maxPlanStringLength} 是本次修复的重要配置\cite{spark_configuration}。旧 5\% event log 在 Spark History Server 的 \texttt{/stages} API 上会触发 JSON 长字符串限制，限制 plan string 后重新运行的最终 event log 体积明显降低，便于长期保留。

\subsection{提交脚本}

提交前先将 \texttt{spark\_jobs} 打包为 zip，再通过 \texttt{spark-submit} 提交到 YARN：

\begin{lstlisting}[style=codexcode]
docker compose --profile yarn-lab exec spark-client \
  /app/scripts/submit_yarn_client.sh /app/configs/yarn-client.yaml yarn-demo
\end{lstlisting}

脚本内部会设置 Hadoop 配置目录、Spark driver host、Python 3.11 解释器路径和 event log 参数，然后调用 \texttt{spark-submit --master yarn --deploy-mode client}。如果用户从前端点击“刷新 Spark”，Flask 的 \texttt{/api/v1/refresh} 会创建 SQLite 作业记录，再由 \texttt{SparkPipelineRunner} 调用 \texttt{SPARK\_SUBMIT\_SCRIPT} 指定的提交脚本。运行完成后，\texttt{SparkPipelineRunner} 从 stdout 中解析 \texttt{Spark run manifest} 路径，读取 manifest 并写入 SQLite 作业表。为了避免后端消息过长，runner 只保留 stdout/stderr tail，完整日志写入 \texttt{data/cache/run\_logs}。

需要理解的是，前端展示的业务指标并不是在每次页面刷新时实时计算。Spark 作业成功后会覆盖 \texttt{data/cache/*.json}；如果当前 YARN 任务仍处于 \texttt{running}，页面仍会显示最近一次成功缓存中的业务指标，同时 Ops 页显示当前任务的 running 状态。这种“旧结果可用、新任务后台刷新”的模式能够保证答辩页面稳定，不会因为 Spark 长任务未完成而空白。

\subsection{YARN cluster mode 入口}

在第一阶段，系统默认使用 YARN client mode，因为 Flask 与 React 仍读取 spark-client 容器中的 \texttt{data/cache}。同时项目新增了 \texttt{configs/yarn-cluster.yaml} 与 \texttt{scripts/submit\_yarn\_cluster.sh}，作为第二阶段 cluster mode 入口。cluster mode 会把 driver 交给 NodeManager 运行，并通过 \texttt{--files} 分发配置文件，通过 \texttt{spark.yarn.appMasterEnv.PYSPARK\_PYTHON} 和 \texttt{spark.executorEnv.PYSPARK\_PYTHON} 固定 Python 3.11，避免 driver 与 executor Python 小版本不一致。由于 cluster mode 下本地 JSON cache 不再天然落在 Flask 可读目录，后续若要把 cluster mode 设为默认刷新路径，需要继续实现 HDFS 输出读取或缓存同步。

\section{核心算法与内存优化实现}

\subsection{禁止 full collect}

早期推荐模块会把 \texttt{recommendation\_features.collect()} 的完整结果带回 driver，再生成大 JSON。这在小样本下能运行，但数据量扩大后会直接增加 driver OOM 风险。优化后，summary、coverage、fallback、duplicate 和 confidence 等质量指标全部使用 Spark 聚合完成；前端展示只收集 preview limit 行数；完整明细写入 Parquet。

\begin{lstlisting}[style=codexcode]
preview_rows = (
    recommendation_features
    .orderBy(F.desc("score"))
    .limit(preview_limit)
    .collect()
)

quality = recommendation_features.agg(
    F.count("*").alias("candidate_rows"),
    F.avg("confidence").alias("avg_confidence"),
    F.sum(F.col("is_fallback").cast("int")).alias("fallback_rows"),
)
\end{lstlisting}

\subsection{WindowExec 警告优化}

Spark 日志中曾出现大量 \texttt{WindowExec: No Partition Defined} 警告。这类警告表示窗口函数没有分区键，Spark 会把数据移动到单分区处理，小样本时只是警告，全量时会变成瓶颈。优化后，ranking 逻辑统一通过 helper 添加全局 rank 或业务分区 rank，避免模块中散落无分区 \texttt{Window.orderBy()}。

\subsection{关联分析组合膨胀控制}

商品关联图谱最容易产生二次级组合膨胀。若某个 session 中商品数过多，直接两两配对会产生 $O(n^2)$ 行。系统加入 \texttt{top\_nodes}、\texttt{max\_pair\_products\_per\_session} 和 pair explosion 指标。质量报告记录 \texttt{eligible\_session\_count}、\texttt{pair\_base\_rows} 和 \texttt{pair\_rows\_per\_input\_row}，用于判断数据规模增长是否仍受控。

\subsection{Parquet 清洗层}

CSV 原始层只作为输入层。清洗后的事件表写入 HDFS Parquet，并按日期字段分区。Parquet 输入对照组直接读取清洗目录，跳过 CSV schema 解析和清洗阶段的部分开销。图\ref{fig:pipeline-flow}展示了从原始 CSV 到前端 Ops 证据的处理流程。

\section{核心业务模块数据计算方法}

本系统的计算入口是 \texttt{spark\_jobs/main.py} 中的 \texttt{run\_job}。一次运行会先读取原始事件表，再生成清洗事件表 \texttt{cleaned\_df}、会话事实表 \texttt{session\_facts} 和特征集市表，随后各业务模块复用这些中间结果。这样做的原因是：事件清洗、去重、日期转换和基础聚合只做一次；转化、推荐、异常、生命周期等模块使用统一口径，避免同一个指标在不同页面出现不一致。

\subsection{基础清洗与元数据口径}

原始数据读取时使用固定 schema，而不是依赖 Spark 自动推断。CSV、JSON、TXT 与 Parquet 入口最终都映射为同一组字段：\texttt{event\_time}、\texttt{event\_type}、\texttt{product\_id}、\texttt{category\_id}、\texttt{category\_code}、\texttt{brand}、\texttt{price}、\texttt{user\_id} 和 \texttt{user\_session}。清洗阶段完成四件事：

\begin{enumerate}
    \item 将 \texttt{event\_time} 转为 \texttt{event\_timestamp}，同时派生 \texttt{event\_date} 与 \texttt{event\_hour}。
    \item 将空品牌、空类目和空会话统一填充为 \texttt{unknown}，把 \texttt{category\_code} 拆出一级、二级类目。
    \item 过滤非法事件类型、空时间、空商品、空用户以及价格小于 0 或大于 100000 的异常行。
    \item 按 \texttt{event\_time + event\_type + product\_id + user\_id + user\_session} 去重。
\end{enumerate}

质量报告中的 \texttt{raw\_rows} 为原始行数，\texttt{cleaned\_rows} 为清洗后行数，\texttt{removed\_rows = raw\_rows - cleaned\_rows}，\texttt{removed\_ratio = removed\_rows / raw\_rows}。重复行、异常价格行、缺失品牌行、缺失必要主键行分别由 Spark filter 或 dropDuplicates 统计。该口径对应前端质量页和 Ops 页的基础数据质量指标。

\begin{sparkcode}{清洗阶段核心代码口径}
cleaned = (
    normalized
    .filter(F.col("event_type").isin(EVENT_TYPES))
    .filter(F.col("event_timestamp").isNotNull())
    .filter(F.col("product_id").isNotNull())
    .filter(F.col("user_id").isNotNull())
    .filter(F.col("price").isNull() | ((F.col("price") >= 0) & (F.col("price") <= 100000)))
    .dropDuplicates(["event_time", "event_type", "product_id", "user_id", "user_session"])
)

quality = {
    "raw_rows": raw_df.count(),
    "cleaned_rows": cleaned.count(),
    "duplicate_rows": raw_df.count() - raw_df.dropDuplicates(event_key_cols).count(),
}
\end{sparkcode}

\subsection{基础看板与排行模块}

基础看板是所有可视化页面的入口。其核心指标来自 \texttt{spark\_jobs/aggregations.py}。行为分布按 \texttt{event\_type} 分组计数；每日事件趋势按 \texttt{event\_date} 或单日场景下的 10 分钟桶分组计数；每日销售额只统计 \texttt{event\_type = purchase} 的价格求和；类目排行按一级类目事件数排序；品牌排行只统计购买事件的订单数和销售额。

关键公式如下：
\[
    \mathrm{total\_sales} = \sum_{\mathrm{event\_type}=\mathrm{purchase}} \mathrm{price}
\]
\[
    \mathrm{view\_to\_purchase\_rate} = \frac{\mathrm{purchase\_count}}{\mathrm{view\_count}}
\]

该模块的特点是直接、稳定、可解释，适合作为答辩时验证 Spark 读取与前端图表是否正常的第一组证据。

\subsection{转化分析模块}

转化分析不直接按事件行计算，而是先把事件压缩成会话事实表。每个 \texttt{user\_session} 只保留首次浏览、首次加购、首次购买时间，以及是否发生浏览、加购、购买。这样可以排除“购买时间早于浏览时间”这类顺序异常，避免把错误路径计入漏斗。合法路径定义如下：

\[
    \mathrm{valid\_cart\_path}=1 \Longleftrightarrow
    t_{\mathrm{view}} \ne \varnothing \land t_{\mathrm{cart}} \ne \varnothing \land t_{\mathrm{cart}} \ge t_{\mathrm{view}}
\]
\[
    \mathrm{valid\_cart\_purchase\_path}=1 \Longleftrightarrow
    t_{\mathrm{view}} \le t_{\mathrm{cart}} \le t_{\mathrm{purchase}}
\]

\begin{sparkcode}{会话事实表与转化漏斗口径}
session_facts = (
    df.groupBy("user_session")
    .agg(
        F.min(F.when(F.col("event_type") == "view", F.col("event_timestamp"))).alias("first_view_ts"),
        F.min(F.when(F.col("event_type") == "cart", F.col("event_timestamp"))).alias("first_cart_ts"),
        F.min(F.when(F.col("event_type") == "purchase", F.col("event_timestamp"))).alias("first_purchase_ts"),
        F.sum(F.when(F.col("event_type") == "purchase", F.coalesce(F.col("price"), F.lit(0))).otherwise(0)).alias("session_revenue"),
    )
    .withColumn("valid_cart_path", F.col("first_cart_ts") >= F.col("first_view_ts"))
    .withColumn("valid_cart_purchase_path", F.col("first_purchase_ts") >= F.col("first_cart_ts"))
)

view_to_cart_rate = cart_sessions / view_sessions
cart_to_purchase_rate = purchase_sessions / cart_sessions
\end{sparkcode}

商品转化模块进一步把粒度降到 \texttt{product\_id + user\_session}，分别统计商品的浏览会话、加购会话、购买会话、销售额和转化率。这样前端可以展示“流量高但购买弱”的商品，也可以为后续运营优化模块提供候选基础。

\subsection{行为路径模块}

行为路径模块关注用户在一个会话中的行为顺序。实现上先对每个会话收集事件结构体，按事件时间排序，再把事件类型数组转为 \texttt{view → cart → purchase} 这样的路径签名。路径统计按签名聚合会话数、加购会话、购买会话、收入、平均步数和平均时长。转移统计则使用相邻事件数组：

\begin{sparkcode}{行为路径与转移边生成}
session_paths = (
    cleaned_df.groupBy("user_session")
    .agg(F.sort_array(F.collect_list(event_struct)).alias("event_structs"))
    .withColumn("events", F.expr("transform(event_structs, x -> x.event_type)"))
    .withColumn("path_signature", F.concat_ws(" -> ", F.expr("slice(events, 1, 8)")))
)

transitions = (
    session_paths
    .select(F.expr("arrays_zip(slice(events, 1, size(events)-1), slice(events, 2, size(events)-1))").alias("pairs"))
    .select(F.explode("pairs").alias("pair"))
    .groupBy(F.col("pair.0").alias("from_event"), F.col("pair.1").alias("to_event"))
    .count()
)
\end{sparkcode}

路径模块输出的 \texttt{exit\_share} 是某个最后事件会话数除以总会话数，\texttt{conversion\_rate} 是该路径或转移关联的购买会话数除以会话数。该口径用于定位“用户在哪一步退出”和“哪些路径更容易购买”。

\subsection{特征集市模块}

特征集市是后续异常、生命周期、实验模块的公共输入。它首先对清洗事件生成 \texttt{event\_key}，其值为事件时间、事件类型、商品、用户、会话和价格拼接后的 SHA-256。随后按三种粒度聚合：

\begin{itemize}
    \item \textbf{日商品特征}：\texttt{dt + product\_id + brand + category\_level1}，统计 views、carts、purchases、unique users、unique sessions、revenue、avg price 与三种转化率。
    \item \textbf{日用户特征}：\texttt{dt + user\_id}，统计 sessions、views、carts、purchases、revenue、active minutes、触达商品数、触达类目数和偏好类目。
    \item \textbf{日类目特征}：\texttt{dt + category\_level1}，统计 views、carts、purchases、unique users、revenue、avg price 与 conversion rate。
\end{itemize}

质量指标中 \texttt{duplicate\_event\_key\_rate = duplicate\_event\_keys / event\_rows}，\texttt{quarantined\_rate = quarantined\_rows / raw\_rows}。新鲜度指标用当前生成时间减去最大事件时间得到 \texttt{freshness\_lag\_hours}，并用最近 N 天窗口识别 late arrival。

\subsection{预测模块}

需求预测模块使用轻量的 rolling baseline，而不是在 driver 端训练复杂模型。Spark 先按全站和一级类目聚合每日需求：

\[
    \mathrm{gmv}_{d,e} = \sum_{\mathrm{date}=d,\mathrm{entity}=e,\mathrm{purchase}} \mathrm{price}
\]

系统只选择全站和 GMV 最高的 top 类目进入 driver，且通过 \texttt{max\_driver\_history\_rows} 限制历史行数。预测时对最近训练窗口求 GMV 与购买数均值，再与上一周期均值比较，得到受限变化率：

\[
    \mathrm{change\_rate} =
    \frac{\overline{\mathrm{gmv}}_{\mathrm{recent}}-\overline{\mathrm{gmv}}_{\mathrm{previous}}}
    {\overline{\mathrm{gmv}}_{\mathrm{previous}}}
\]

未来第 $i$ 天的预测值为：
\[
    \widehat{\mathrm{gmv}}_{i} =
    \max(0, \overline{\mathrm{gmv}}_{\mathrm{recent}} \times (1 + \mathrm{clip}(\mathrm{change\_rate}, -0.25, 0.25) \times i / h))
\]

若历史天数不足，则使用 \texttt{sparse\_baseline\_fallback} 并扩大预测区间。回测模块计算 WAPE，风险模块根据未来 GMV 相对近期均值的下降比例输出 high/medium 风险。

\subsection{关联图谱模块}

关联图谱以会话内共同出现商品为基础。第一步把事件压缩为 product-session 表：同一会话同一商品只保留是否浏览、是否加购、是否购买、行为次数和收入。第二步选出收入、购买和浏览靠前的 top 商品，避免所有商品两两组合。第三步过滤商品数过多的 session，因为单个 session 有 $n$ 个商品时会产生 $n(n-1)/2$ 条候选边。第四步自连接生成商品对，并分别计算 co-view、co-cart、co-purchase 三类关系。

边指标口径如下：
\[
    \mathrm{support}(A,B)=|\{s: A \in s \land B \in s\}|
\]
\[
    \mathrm{confidence}(A \rightarrow B)=\frac{\mathrm{support}(A,B)}{\mathrm{sessions}(A)}
\]
\[
    \mathrm{lift}(A,B)=\frac{\mathrm{support}(A,B)\times \mathrm{total\_sessions}}
    {\mathrm{sessions}(A)\times \mathrm{sessions}(B)}
\]

\texttt{affinity\_quality} 记录 \texttt{eligible\_session\_count}、\texttt{pair\_base\_rows} 和 \texttt{pair\_rows\_per\_input\_row}。如果这些指标异常升高，说明组合膨胀风险变大，需要收紧 \texttt{top\_nodes} 或 \texttt{max\_pair\_products\_per\_session}。

\subsection{Cohort 留存模块}

Cohort 模块只使用购买事件。系统先找到每个用户的首次购买日期，并将首次购买月份作为 cohort；然后把用户每个月的购买聚合为 purchase cycle，计算当前购买月份与 cohort 月份之间的 \texttt{period\_index}。留存矩阵中的核心指标为：

\[
    \mathrm{retention\_rate}_{c,p}=
    \frac{\mathrm{active\_users}_{c,p}}{\mathrm{cohort\_users}_{c}}
\]
\[
    \mathrm{repurchase\_rate}_{c,p}=
    \frac{\mathrm{repurchase\_users}_{c,p}}{\mathrm{cohort\_users}_{c}}
\]

价值曲线在留存矩阵上做窗口累计，得到 \texttt{cumulative\_revenue}；复购间隔根据用户相邻购买周期差值分桶；cohort segment 按首次类目、复购率和收入识别高风险 cohort，并给出再营销建议。

\subsection{商品组合与购物车挽回模块}

商品组合模块先对事件补齐一级类目、品牌和价格带。价格带划分为 \texttt{budget}、\texttt{mass}、\texttt{premium}、\texttt{luxury} 和 \texttt{unknown}。类目、品牌、价格带分别聚合 views、carts、purchases、revenue、avg price 和转化率，并计算收入占比与购买占比。商品集中度使用收入份额平方作为 HHI 贡献：

\[
    \mathrm{hhi\_contribution}_{i} = \mathrm{revenue\_share}_{i}^{2}
\]

购物车挽回模块把粒度设为 \texttt{user\_session + product\_id}。若商品在同一会话中出现加购事件，则进入购物车事实表；若后续存在购买且购买时间不早于首次加购，则 \texttt{recovered=1}；否则 \texttt{abandoned=1}。放弃金额计算为 \texttt{cart\_value}，其中 \texttt{cart\_value = unit\_price × cart\_events}。队列优先级为：

\[
    \mathrm{priority\_score} = \mathrm{abandoned\_value} \times \mathrm{abandonment\_rate}
\]

如果移除率较高，推荐动作是检查商品摩擦；如果放弃率超过阈值，推荐动作是挽回提醒或优惠。

\subsection{收入归因模块}

归因模块先把每次购买生成唯一 \texttt{purchase\_id}，再把同一会话中购买之前的 \texttt{view}、\texttt{cart} 和 \texttt{remove\_from\_cart} 事件作为触点。每个触点同时计算四种 credit：

\begin{itemize}
    \item \textbf{First-touch}：第一个触点获得全部购买收入。
    \item \textbf{Last-touch}：最后一个触点获得全部购买收入。
    \item \textbf{Linear}：所有触点均分购买收入。
    \item \textbf{Time-decay}：越接近购买的触点权重越高，权重为 \(\mathrm{base}^{\mathrm{reverse\_position}-1}\)。
\end{itemize}

\begin{sparkcode}{收入归因 credit 计算}
weighted = (
    joined
    .withColumn("touch_count", F.count("*").over(by_purchase))
    .withColumn("position_before_purchase", F.row_number().over(asc))
    .withColumn("reverse_position_before_purchase", F.row_number().over(desc))
    .withColumn("linear_credit", F.col("purchase_revenue") / F.col("touch_count"))
    .withColumn("first_touch_credit", F.when(F.col("position_before_purchase") == 1, F.col("purchase_revenue")).otherwise(0.0))
    .withColumn("last_touch_credit", F.when(F.col("reverse_position_before_purchase") == 1, F.col("purchase_revenue")).otherwise(0.0))
    .withColumn("time_decay_weight", F.pow(F.lit(decay_base), F.col("reverse_position_before_purchase") - 1))
    .withColumn("time_decay_credit", F.col("purchase_revenue") * F.col("time_decay_weight") / F.sum("time_decay_weight").over(by_purchase))
)
\end{sparkcode}

之后系统分别按商品、品牌和类目聚合 credit，得到实体贡献；再统计高频路径和助攻机会。归因质量指标关注购买是否能找到触点，即 \texttt{attribution\_coverage\_rate}。

\subsection{运营优化与推荐模块}

运营优化模块的候选来自商品级转化统计。系统先计算 views、carts、purchases、funnel purchases、revenue、avg price、revenue per view 等指标。为了避免小样本商品因为少量购买被高估，购买率使用两层稳健化：一层是带先验权重的收缩购买率，另一层是 Wilson lower bound。候选置信度为：

\[
    \mathrm{confidence} =
    \min(1,\sqrt{\mathrm{views}/500}) \times
    (0.5 + 0.5 \times \min(1,\mathrm{wilson}/\mathrm{global\_purchase\_rate}))
\]

优化目标是在总预算、运营位数量、类目上限和品牌上限约束下，选择“商品-动作”组合，使风险调整后的增量 GMV 最大。若本地没有 Gurobi 或求解失败，系统降级为贪心排序，仍输出可解释计划和 \texttt{degraded\_greedy} 状态。

推荐模块复用商品转化特征与优化计划。商品分数由购买转化率、加购率和每浏览收入组成：
\[
\begin{aligned}
    \mathrm{product\_score}
    &=0.55 \times \mathrm{view\_to\_purchase}
      +0.25 \times \mathrm{view\_to\_cart} \\
    &\quad +0.20 \times \min(\mathrm{revenue\_per\_view}/500,1)
\end{aligned}
\]

目标会话按最近事件和偏好类目抽样。推荐时优先从用户偏好类目中选择未看过的高分商品；如果数量不足，再从优化计划或全局高分商品中兜底。最终按 \texttt{score} 和 \texttt{confidence} 排序，每个会话保留 top-k。质量报告统计覆盖会话数、fallback 率、平均置信度、重复推荐率和无效商品率。

\begin{sparkcode}{推荐商品分与会话 top-k 计算}
product_features = (
    cleaned_df.groupBy("product_id", "brand", "category_level1")
    .agg(
        views.alias("views"),
        carts.alias("carts"),
        purchases.alias("purchases"),
        revenue.alias("revenue"),
    )
    .withColumn("view_to_cart_rate", F.col("carts") / F.col("views"))
    .withColumn("view_to_purchase_rate", F.col("purchases") / F.col("views"))
    .withColumn("revenue_per_view", F.col("revenue") / F.col("views"))
    .withColumn("product_score", F.col("view_to_purchase_rate") * 0.55
        + F.col("view_to_cart_rate") * 0.25
        + F.least(F.col("revenue_per_view") / 500.0, F.lit(1.0)) * 0.20)
)

rank_window = Window.partitionBy("user_session").orderBy(F.desc("score"), F.desc("confidence"))
recommendations = candidates.withColumn("rank", F.row_number().over(rank_window)).filter(F.col("rank") <= top_k)
\end{sparkcode}

\subsection{异常检测与生命周期模块}

异常检测模块复用特征集市中的日类目和日商品特征。每条监控信号由 \texttt{dt + entity\_type + entity\_id + metric} 组成，指标包括 views、purchases、revenue、conversion rate 等。系统使用中位数和 MAD，而不是均值和标准差，原因是电商数据常有促销尖峰和长尾商品，MAD 对极端值更稳健。robust z-score 计算为：

\[
    z_{\mathrm{robust}} =
    \frac{|x-\mathrm{median}(x)|}{1.4826 \times \mathrm{MAD}(x)}
\]

若历史点数不足，状态为 \texttt{watch}；若 z-score 超过 warning 或 critical 阈值，则生成对应告警；若当前值为 0 且基线量级高于最小流量阈值，也视为 critical。

生命周期模块以日用户特征为输入，按用户聚合活跃天数、会话数、浏览数、加购数、购买数、收入、购买天数、最近活跃日期和偏好类目。分层规则是确定性的 RFM + engagement：高收入且多购买天数为 \texttt{champion}；达到高价值阈值为 \texttt{high\_value}；有多日购买为 \texttt{loyal}；有购买为 \texttt{buyer}；只有加购为 \texttt{cart\_intent}；只有浏览为 \texttt{browser}。风险带则由最近活跃天数和购买证据决定：超过 \texttt{at\_risk\_recency\_days} 为 \texttt{at\_risk}，无购买但有加购为 \texttt{convert\_intent}。

\subsection{实验分流与 Ops 证据模块}

实验分流模块不直接在线投放，而是生成课程设计所需的可解释实验准备数据。实验目录包含生命周期再激活、推荐个性化和商品运营位三类实验。用户是否 eligible 由生命周期分层决定；进入实验后通过 \texttt{hash(user\_id, experiment\_key)} 生成稳定桶，桶值小于 treatment split 的用户进入 treatment，否则进入 control。这样同一份数据重复运行时，用户分组保持稳定。

实验 guardrail 检查包括 treatment/control 用户数、分组不平衡率、推荐覆盖率和优化计划是否存在。预期增量 GMV 不是实际因果效果，而是用于课程系统演示的计划值：
\[
    \mathrm{expected\_incremental\_gmv} =
    \mathrm{expected\_uplift\_rate} \times \max(\mathrm{avg\_order\_value}, 50)
\]

Ops 证据模块读取 run manifest、SQLite job 表、Spark History 指标和 benchmark 结果。它不重新计算业务指标，而是把一次运行的输入、输出、质量、耗时、application id 和存储清理策略串起来，形成答辩时可追溯的“证据链”。因此，业务页面回答“数据是什么”，Ops 页面回答“数据从哪里来、怎么算完、运行是否成功”。

\subsection{实验结论}

从实验结果可以得到三点结论。第一，仅将 Spark 提交到 YARN 不会自动解决性能和内存问题，YARN-only 组反而因为调度、容器和 HDFS 访问开销表现最慢。第二，AQE 和算法层限流是关键优化，能显著降低不必要 shuffle、单分区窗口和 driver 端大收集风险。第三，Parquet 输入是后续扩展到更大数据规模的必要基础，但需要与分区、列裁剪和模块级缓存一起使用。

因此，本课题最终结论应表述为：在本机 ARM64 Docker Hadoop YARN 环境中，系统已经显著降低 OOM 风险，并通过 1\%/5\% pipeline benchmark、event log 指标和 20 万行典型模块 benchmark 给出证据。按本次实验取舍，不再强行运行全量 Oct+Nov；全量处理可作为后续资源边界扩展，在更高 Docker 内存、更多 executor 或云端集群环境中继续验证。
